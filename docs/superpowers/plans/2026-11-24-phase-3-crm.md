# Phase 3: CRM and the Remaining Channels Implementation Plan

> **Review log:** written 2026-11-24 from the roadmap's Phase 3 scope and the owner's decisions; owner answers to the open questions and the four-lens plan review (correctness, security, performance, maintainability) folded in the same day (summary in "Review changes (2026-11-24)" at the end). Run the four-lens **branch** review before each tier merges.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** B&C gets a weekly digest built for each reader, writes blog articles that land on their Shopify blog, drafts quotes that become Shopify draft orders with a person confirming every write, and — as approvals land — keeps Instagram and Messenger messages in our own database, sees customer records linked to Shopify customers with notes, works a follow-up queue with AI conversation summaries, and sees Google Ads spend next to Meta's.

**Architecture:** Three tiers, each its own branch and merge. Tier 1 needs no outside approval: a `digest.build` job writing one `Digest` row per reader and week; a `BlogArticle` table written by a new article writer and pushed with Shopify `articleCreate`/`articleUpdate`; a `Quote` table pushed as a Shopify draft order. Every Shopify write goes through one confirmed-write module (`server/shopify/writes.ts`): preview → person confirms → write at most once → audit. Tier 2 adds one signed webhook route for Meta and Instagram that only stores the encrypted body and queues an `inbox.event` job; the job writes `InboxConversation`/`InboxMessage`; a `SHOPIFY_CUSTOMERS` data source syncs Shopify customers into `Customer`; follow-ups are Phase 1 tasks in a new `CRM` area. Tier 3 adds a `GOOGLE_ADS` provider and data source that fill the existing `AdDay` table, read by the existing Ads tab with a platform switch.

**Tech Stack:** Next.js route handlers, Prisma 6 on Postgres (Neon), zod, vitest (`npm test`, `npm run test:db`); web Next.js + React behind `WEB_FEATURES` flags (English copy only: the web app has no i18n); mobile Expo (shared types, locale strings, CRM task area label, the stored inbox through the existing endpoints); shared types synced with `npm run sync:shared`; AI through `server/ai/provider.ts` (`generateObject`, OpenAI).

**Estimate:** 33.5 dev days (roadmap: 30; re-baselined after the plan review added reconciliation, deletion, retention and access-audit work). Foundation 1.5 d; tier 1: 13.5 d; tier 2: 12.5 d; tier 3: 5 d; docs 1 d. Tasks 8, 12 and 14 are split in two. Approvals are calendar time, not counted.

## Why

The roadmap's Phase 3 closes B&C's CRM and Ads sections. Today the inbox is read live from Meta and nothing is kept (`server/customers/inbox.ts:10-14`), so nothing can be followed up, summarised or linked to a customer; quotes and blog posts are done by hand in Shopify; Google Ads spend is not seen; and nobody gets a weekly picture. Phase 2 put Shopify orders and Meta Ads in our database; Phase 3 builds on that.

**Not building:** our own quote system (Shopify draft orders are the quote), a PDF generator (a print stylesheet), a sales pipeline before messages are stored.

## Decisions (owner, 2026-11-24)

1. **Build order by tier.** Tier 1 first (no outside approvals): weekly digest, blog to Shopify, quotes as Shopify draft orders. Tier 2 when approvals land: customer records, stored inbox, follow-up queue. Tier 3: Google Ads when the developer token arrives; **the owner's side applies for the token**, tier 3 waits for it.
2. **Permissions.** A new **`crm.manage`** key, separate from `crm.read`, for customer records, notes and quotes. Default holders Owner, Admin, Project admin, Manager. The Client reviewer gets neither `crm.manage` nor `inbox.read` by default; **the permission matrix decides** (nothing in code blocks it). **Approvers keep `inbox.read`** (can be unticked in the matrix).
3. **Messages kept 13 months.** When storing is turned on for an account, the last **30 days** of conversations are also loaded where Meta allows it.
4. **Follow-ups:** a customer message unanswered for **24 h** creates a follow-up task, **role-owned** by the project role that handles the inbox (anyone with `inbox.read` can take it), **one per conversation**, **closed automatically** when someone replies.
5. **Quotes:** drafted in our app, created in Shopify as draft orders. Valid **30 days**; reminder tasks at **day 7 and day 21** if unpaid; **expired at day 30**. The customer gets **Shopify's own invoice email**, sent with `draftOrderInvoiceSend` only when a person clicks Send.
6. **Blog:** an article is created in Shopify **hidden** first; the team checks it; a person clicks **Publish** in our app. Default blog = the store's first blog unless one is picked; author = the **brand name**.
7. **Digest:** **in-app for everyone every Monday**; **email is opt-in per person**, with a one-click signed `List-Unsubscribe`. Each reader's digest is built from their own permissions.
8. **Shopify scopes** come from the owner's separately built Shopify app (another session); we consume its token through the existing paste screen. Scopes it must add are listed under "Waiting on others".
9. All of Phase 3's Sales & CRM screens sit behind a `crm` web flag at the "Sales & CRM" menu slot.

## My calls (owner may override)

1. **Permission use.**
   - `crm.manage` ("See customer records and notes, and write quotes"), group `crm`, gates customers, notes, quotes and the draft-order writes. `crm.read` keeps meaning "orders and sales totals".
   - The stored inbox, its summaries and the follow-up queue reuse **`inbox.read`**; sending a reply stays **`publish.execute`** as today (`customers/inbox/[connectionId]/[conversationId]/route.ts:23`).
   - Blog: write with `content.create`; approve with `content.approve` under the same own-work rule as posts (`hasOtherHolder`, `server/auth/permissions.ts:93`); push and publish to Shopify with **`publish.execute`**. No `content.publish` key (it would duplicate `publish.execute`).
2. **Task area `CRM`** (deferred from Phase 1, spec `2026-11-23-phase-1-tasks-design.md:39`): a task whose `areas` include `CRM` is visible only to a viewer holding `inbox.read` or `crm.manage` on that brand. A client reviewer sees one only if the matrix gives their role one of those keys (then the client rules of Phase 1 apply on top). Follow-ups and quote reminders are CRM tasks, so they get Phase 1's owners, due dates, overdue notices and Today counts. Their titles never carry message text or customer names.
3. **Confirmed writes to Shopify** (quotes, invoices, articles): `POST …/preview` returns exactly what will be written (every link target listed) and a `confirmToken`; `POST …/confirm {confirmToken}` re-checks the permission, re-reads the row, rebuilds the payload, refuses if the hash changed (409 "This changed since you checked it"), then writes at most once. States and reconciliation in Task 4. Every write is audited (`shopify.<action>`), metadata ids and counts only.
4. **Shopify writes never mark the connection for reconnect on a missing scope.** `ACCESS_DENIED` on a write → "Add <scope> to your Shopify app"; the catalogue sync is untouched (as `fetchOrders` does for `read_orders`, `server/data/shopify-orders.ts:152-153`).
5. **Flags:** `crm` (Sales & CRM hub: quotes in tier 1; inbox, customers, follow-ups in tier 2), `blog` (Website area), `digest`; Google Ads under the existing `ads` flag. All three new flags are registered in Task 1. The server API is unflagged but permission-checked. With `crm` on and `crm.manage` or `inbox.read`, Spark's "Sales & CRM" slot opens `/crm` (same pattern as Beat, `web/lib/nav.ts:87-90`).
6. **Digest:** built per brand-local week (Monday–Sunday just ended in **each brand's** zone); one `Digest` row per (user, workspace, week). Sections only when the reader holds the key on that brand: content (`brand.read`), tasks (`tasks.read`, through task visibility), SEO (`analytics.read`, latest 7 **complete** Search Console days), posts (`analytics.read`), sales (`crm.read`), ads (`ads.read`), quotes (`crm.manage`), inbox (`inbox.read`). **Why not a notification:** notifications inner-join `Task` (`server/notifications/list.ts:18`); a digest is a page of figures, not a task event, so it gets its own page and the bell is untouched. **Web-only for now; the phone later.**
7. **Stored inbox retention:** 13 months from `sentAt`; on disconnect, the connection's stored messages are purged and the page/account unsubscribed; on Meta data-deletion or deauthorize callbacks, the same plus the connection is revoked. Attachments stored as type only.
8. **Webhook events** are stored encrypted in `WebhookEvent`; job payloads carry only the event id. Job rows live 30 days (`server/jobs/runner.ts:249`), so tier-2 handlers throw only **fixed-reason errors** (no customer text reaches `Job.lastError` or logs). Processed events are deleted at once; unprocessed ones after 7 days.
9. **The reply audit stops storing the reply text.** `inbox.reply.sent` stores `text` today (`server/customers/inbox.ts:160`); from Task 11 it stores `length` and the stored message id, and a migration blanks `text` in existing rows.
10. **Customers:** a `SHOPIFY_CUSTOMERS` data source on the existing `data.sync` job; allow-listed fields (id, display name, default email, default phone, number of orders, amount spent, tags, created/updated, marketing state; field names re-checked against the pinned API version, Task 14a), no addresses. Orders link to customers by a new nullable `ShopOrder.customerId`, filled only when `read_customers` is granted (orders synced before that stay unlinked until their next update or a re-read). Conversations link to a customer only by a person. Customer rows are kept while the source is on; turning it off or disconnecting Shopify purges them; every view, search and erasure is audited by id.
11. **Google Ads** is a new provider `GOOGLE_ADS` with its own Google login asking `adwords` only (plus `openid email`), never added to the existing `GOOGLE` login (`server/integrations/providers.ts:299-310`). Purchases = conversions whose `conversion_action_category` is `PURCHASE` (second GAQL query). Daily window re-reads the last 14 days; backfill 180 days in 30-day windows.
12. **`AdDay.purchases` becomes `Decimal(14,2)`** (Google conversions are fractional). Lossless widening migration, run off-peak; readers updated in the same task (Task 18).
13. **Article bodies** are structured blocks rendered to HTML on the server from an allow-list (`h2 h3 p ul ol li strong em a[href http(s)]`).
14. **Ownership with the Phase 2 follow-up:** the follow-up owns `AdPlatform.GOOGLE` (its Task 3); Task 17 adds it with `ADD VALUE IF NOT EXISTS` so either order works. **Phase 3 Task 18 owns the `platform` parameter in `server/data/ads-read.ts`** (default `META`, so the follow-up's pacing code is unchanged); Task 19 depends on Task 18 only.
15. **New data source kinds** follow one name each and get a `DATA_SOURCE_SLUGS` entry (`shared/data-sources.ts:9`): `SHOPIFY_QUOTES` (quote status reads; a registered kind so it gets `lastResult`, the sweep and Sync now for free), `SHOPIFY_CUSTOMERS`, `GOOGLE_ADS`.
16. **Shopify API version:** new mutations and the customer query use one new constant `SHOPIFY_WRITE_API_VERSION`, pinned to the current stable version at build; reads stay on `2025-07` until re-checked.

## Review focus

1. A forged, replayed or duplicated Meta/Instagram/Shopify webhook never writes a row twice or at all; a valid one is answered in under a second whatever the queue is doing; events reach only brands that turned storing on.
2. No customer text or PII lands in a log, job payload, `Job.lastError`, audit row, error, or another brand's rows; deletion (disconnect, retention, Meta callback, Shopify redact, per-customer erasure) reaches every copy, encrypted webhook events and old audit text included.
3. Every Shopify write is the exact thing a person confirmed, happens at most once (timeouts reconciled, never re-sent blind), is audited, and a missing write scope never marks the store "Needs reconnect".
4. A reader's digest (in-app and email) holds only what their **current** permissions on each brand show.
5. CRM-area tasks are invisible to people without `inbox.read`/`crm.manage` in every reader (list, search, counts, notifications, Today, digest).
6. Google rows never change Meta totals and vice versa; fractional conversions are kept exactly.
7. Webhook, data and digest jobs never delay publishing jobs.

## Tier 1: no outside approvals (13.5 d) — merge 1

### Task 2: Digest content per reader (1.5 d)

**Files:** Create `server/digest/build.ts`, `shared/digest.ts` (export from `shared/index.ts`). Modify `prisma/schema.prisma` (`Digest`; `User.digestEmail Boolean @default(false)` — opt-in), migration `<ts>_digest`. Tests `tests/digest-build.test.ts`, `tests/db/digest-build.db.test.ts`.

**Data model:**
```prisma
/// One reader's weekly digest for one workspace (server/digest/build.ts). Re-filtered by current permissions on read.
model Digest {
  id          String    @id @default(cuid())
  userId      String
  workspaceId String
  weekStart   DateTime  @db.Date   // Monday of the covered week (UTC label; each brand section carries its own range)
  body        Json      // DigestBody: per brand, the sections the reader could see at build time
  emailedAt   DateTime?
  createdAt   DateTime  @default(now())
  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@unique([userId, workspaceId, weekStart])
  @@index([workspaceId, weekStart])
  @@index([createdAt])
}
```

**Interfaces:**
- `brandSections(brandId, permSet, week) → BrandSections` computed **once per (brand, distinct permission set)** per run and shared by readers with the same set (memo keyed by sorted keys), calling existing read functions only (no second copy of any SQL). Tasks are the exception: counts depend on the viewer (`visibleTaskSql`), computed per reader.
- `buildDigest(userId, workspaceId, weekStart) → DigestBody | null`: per non-archived brand the user reaches, permissions via `permissionsOf`; the week = the brand-local Monday–Sunday that has ended in that brand's zone (`brandTimeZone`). SEO uses the latest 7 complete Search Console days (Google lags ~2-3 days; labelled with its dates).
