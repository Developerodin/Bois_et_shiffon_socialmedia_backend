## Facts from the code (checked 2026-11-27 on `main`)

**Quotes**
- `Quote` is at `prisma/schema.prisma:2065`; `enum QuoteStatus { DRAFT CREATED SENT ACCEPTED EXPIRED CANCELLED }` is
  at `:2055`. There is no DECLINED status.
- `version` is bumped by edits only, and a Shopify confirm token binds it. There is no history: `editQuote`
  (`server/quotes/quotes.ts`) overwrites the quote with `updateMany`, **outside any transaction**, then writes the
  audit row.
- `quoteAction` `revise` changes SENT → **CREATED** whatever the `shopifyId`. CREATED is labelled "In Shopify" on the
  web (`quotes-board.tsx:29`), and `nextQuoteStep` then offers "update"/"invoice", both of which need a `shopifyId`.
- `deleteQuote` cancels a quote that isn't a never-sent draft and keeps the Shopify draft. `INVOICE_STAYS_PAYABLE`
  talks about Shopify's invoice.
- `contactName`/`contactEmail` hold a PII snapshot. `customerId` and `conversationId` are columns with no FK
  ("tier 2"), and nothing writes them.
- Status sync (`server/quotes/status-sync.ts`, the SHOPIFY_QUOTES data source, daily):
  - It **returns at once for Shopify-MCP-only brands**, before expiry and reminders.
  - Expiry runs on open quotes past `validUntil`. A quote with no `shopifyId` expires without being read.
  - Reminders (`remind`) are created on day 7 and day 21 as CRM tasks owned by `sentById`, with `requestId =
    reminderKey(...)`. Their text says "Shopify invoice".
  - Cancelled and expired quotes are watched for 60 days in case they are paid.
- `confirmInvoice` `onDone` sets SENT, `sentAt`, `validUntil` (send day + 30 brand days) and `sentById`, and closes the
  previous send's reminders.
- **Quotes don't reach Shopify for B&C:** `askCartWriteAdapter` answers `NOT_CONNECTED` to every write
  (`server/shopify/adapter.ts`).

**Conversations**
- `server/customers/inbox.ts` reads Instagram and Messenger live; nothing is stored.
- The mobile app has its live inbox and People screens. The web has no inbox page.
- `draftReply` (`server/customers/drafts.ts`) handles the kinds `review | message | googlePost`. Customer text is
  wrapped in `<customer>` with `<>` stripped. Limits: 60 drafts per hour per brand and 40 per hour per user, on
  route `content.create`. It is used on mobile only.

**Customers**
- There is no Customer model, and `ShopOrder` holds no customer data.
- `Opportunity` means content ideas, so the pipeline model needs a different name.

**Tasks and permissions**
- `Task.requestId` has `@@unique([brandId, requestId])` (`schema.prisma:1530`). Quote reminders use it for
  one-per-key creation.
- Role ownership:
  - `ownerRoleId` must be a PROJECT role (`taskOwnerRoleWhere`, `server/tasks/links.ts:17`) that holds `tasks.read`
    and is not a client grant. For CRM tasks it must also hold a CRM key.
  - Holders are resolved through `BrandMember.roleId` (`assigneesOf`, `server/notifications/tasks.ts:28`;
    `ownClause`, `server/tasks/access.ts:108`).
  - Owner and Admin are WORKSPACE roles and **can't own a task**. Project admin, Manager and Approver are PROJECT roles
    (`permissions.catalog.ts:45-60`), so they can.
- `canBeAssigned(tx, scope, userId, { areas: ["CRM"] })` checks the CRM keys. `brandMemberPerms(tx, scope, userId,
  key)` checks a person's key on a brand (workspace role or non-client grant).
- `crm.manage` covers customer records, notes and quotes. `inbox.read` covers customer messages.
  Manager holds `crm.manage`, `inbox.read` **and `integrations.manage`**, but **not `tasks.all`**. The Approver holds
  `inbox.read` only (no `content.create`, so no AI drafts). Only Owner and Admin hold the workspace key
  `members.manage`.
- Web: `/crm` is gated by the `crm` flag and **`crm.manage` only** (`app/(shell)/crm/page.tsx`, `lib/nav.ts:57,113`).
  An Approver, who works the inbox, can't reach it.
- `featureAccess` takes a single `perm`.
- `hitRateLimit(key, n, ms)` (`server/auth/rate-limit.ts`). `lockRow` (`server/services/publishing.ts`).
- The daily sweep's later steps each sit in their own try/catch (`server/jobs/runner.ts`, `dailySweep`).

## Decisions (my calls; the owner may override)

1. **One conversation model for every channel, ready for Gmail.**
   - `Conversation` + `ConversationMessage` replace Phase 3 Task 11's `InboxConversation`/`InboxMessage`.
   - `channel` is `LOGGED | INSTAGRAM | MESSENGER`. Phase D adds `GMAIL` with one `ADD VALUE` migration.
   - A thread from an outside system is keyed by `(connectionId, externalThreadId)`:
     - Gmail: `threadId`; one sender can have many threads.
     - Meta: the customer's PSID/IGSID, so each person has one thread per connection.
   - `customerExternalId` holds the sender's id (PSID/IGSID, or a lower-cased email address).
   - `subject` is allowed on every channel.
   - A message's `externalId` (Meta `mid`, Gmail message id) is unique per conversation.
   - Phase B and Phase D only *add* nullable columns (for example Meta's conversation id) and enum values. Nothing is
     reshaped.
2. **A customer is a person; a company is optional.**
3. **Identities, not columns.** `CustomerIdentity(kind, value)` with kinds `EMAIL | PHONE | INSTAGRAM | MESSENGER |
   SHOPIFY`.
   - A value is unique per brand and kind.
   - Emails are lower-cased.
   - Phones keep a leading `+` and digits only. Without a `+`, the digits only. 6-15 digits.
   - Adding an identity that belongs to another customer → 409 with that customer's id and name. The caller holds
     `crm.manage`, so the name is not a leak.
4. **Merge is done by a person, never automatically.** Two customers can never share an identity (the unique rule), so
   suggestions match on the **same display name** (trimmed, case-insensitive) within the brand.
   - The person can also pick any customer through search.
   - The merge moves identities, notes, conversations, deals and quote links onto the survivor, deletes the other row,
     and is audited with both ids.
   - It is one transaction, bound to both rows' `updatedAt`.
   - There is no un-merge, and the dialog says so.
5. **The follow-up state is derived, not stored.** Stored inputs: `lastMessageAt` and `lastFromCustomer` (from the
   latest message by `sentAt`), `waitingSince`, `closedAt` and `nextActionDue`. States:
   - **Closed:** `closedAt` is set.
   - **Waiting on the customer:** we wrote last (`waitingSince` = our message's `sentAt`), or a person marked it
     waiting (`waitingSince` = now). After **7 days** of waiting it is overdue and back in the queue (O4).
   - **Needs reply:** the customer wrote last and it isn't marked waiting. It is overdue after 24 h.
   - **Overdue** also covers a `nextActionDue` before today, in the brand's zone.
   - A customer message clears `waitingSince`. Our message sets it. Closing a conversation clears its open follow-up
     task. A new customer message reopens it.
6. **Owner and next action** are on `Conversation`, `Deal` and `Customer`: `ownerId`, `nextAction` (up to 200
   characters) and `nextActionDue` (a brand-local date). Who can be the owner:
   - a conversation's owner must hold `inbox.read` on the brand;
   - a deal's or customer's owner must hold `crm.manage`;
   - both are checked with `brandMemberPerms`, so client grants never count.
7. **The pipeline model is `Deal`**, with `DealStage { NEW CONTACTED PROPOSAL NEGOTIATION WON LOST }` (O2).
   - Its value is `Decimal(14,2)` with a currency, never summed across currencies.
   - Won and Lost need a reason from a short list (`price`, `timing`, `competitor`, `no_response`, `not_a_fit`,
     `quote_accepted`, `other`) plus optional text of up to 500 characters.
   - Moving to Won or Lost sets `closedAt`. Moving back to an open stage clears it.
8. **Quote → deal stage mapping (O2).** A hook moves a deal **forward only**, and never moves a deal that is already Won
   or Lost:

   | Quote event (on a quote with `dealId`) | Deal stage |
   |---|---|
   | created or linked | unchanged (New and Contacted are set by people) |
   | SENT (Shopify invoice, or sent by hand) | NEW/CONTACTED → **PROPOSAL** |
   | Revise of a SENT quote | PROPOSAL → **NEGOTIATION** |
   | ACCEPTED (Shopify payment, accepted by hand, or a late payment found by the sync) | any open stage → **WON**, reason `quote_accepted` |
   | DECLINED / EXPIRED / CANCELLED, when the deal then has no open quote | unchanged; the deal shows "Its last quote was declined/expired/cancelled: mark it lost?" (derived on read) |

   Each move is audited as `deal.stage` with `{ from, to, quoteId, auto: true }`.
9. **DECLINED is set by a person** from CREATED, SENT or EXPIRED, with an optional reason of up to 500 characters
   (`Quote.declinedReason`).
   - It closes the payment reminders.
   - The status sync watches a DECLINED quote that is in Shopify for 60 days, like CANCELLED/EXPIRED. If it is paid
     anyway it becomes ACCEPTED, with a team note.
   - Shopify's draft is left in place, and the dialog says so.
10. **Quote version history:** every edit writes the **previous** state to `QuoteVersion` **in the same transaction** as
    the edit (`editQuote` is restructured to do this).
    - The snapshot holds the lines, discount, customer note and totals, with **no contact name or email**.
    - A revise also snapshots, marked `sent: true`.
    - A concurrent edit of the same version → one row and one 409 (the `version` guard, plus
      `@@unique([quoteId, version])`).
11. **Logged messages** are typed in by a person:
    - medium `EMAIL | PHONE | IN_PERSON | WHATSAPP | OTHER`;
    - direction in or out;
    - a date (not in the future, not older than 13 months);
    - text of up to 4,000 characters.
    Logging never sends anything. A logged conversation must have a customer (erasure always reaches it).
12. **Web first.** Mobile gets the synced shared types only. Its live inbox and People screens are unchanged.
13. **Overview "customer follow-ups"**: `GET …/crm/follow-ups/counts` returns `{ needsReply, overdue, waiting, mine }`
    for the viewer (needs `inbox.read`).
    - The web shows it in **one small component**, `components/crm/follow-up-counts.tsx`, plus one line in
      `components/workspace/workspace.tsx`. It is built last because the overview stream is editing that file.
    - It is fetched once per Overview mount. There is no poller.
14. **Service queue: not building.** The feature list says "if the team also uses CRM for delivery issues". Adding
    another `pipeline` column later is additive. The owner can ask for it.
15. **Access requests (GDPR Art. 15):** a one-customer JSON export. Erase and export need `crm.manage` on the brand
    **and a workspace role holding `members.manage`** (Owner/Admin; Manager and Project admin hold
    `integrations.manage`, so that key wouldn't limit it). They are refused to client grants, limited to 10 an hour
    per user, and audited by id. This reverses Phase 3's "no customer export".
16. **Quotes by hand until AskCart writes exist** (O1). For a quote with **no `shopifyId`**:
    - **Mark sent:** DRAFT/CREATED → SENT. Sets `sentAt`, `validUntil` (30 brand days, as for an invoice) and
      `sentById`. The day 7 and day 21 reminders follow through the status sync.
    - **Mark accepted:** SENT/EXPIRED → ACCEPTED.
    - **Revise** goes to **DRAFT**, not CREATED (CREATED means "in Shopify").
    - Once a quote is in Shopify, the hand actions are refused with 409, re-checked in the update's `where`.
    - The status sync's `shopifyMcpOnly` return moves **after** expiry and reminders, so hand-sent quotes expire and
      get reminders on those brands too. Only the Shopify reads are skipped.
    - Reminder and cancel copy says "the quote" for hand-sent quotes.
17. **Visibility follows the keys.**
    - `/crm` opens with the `crm` flag and **either** `crm.manage` or `inbox.read`.
    - Tabs: Follow-ups needs `inbox.read`. Customers, Pipeline and Quotes need `crm.manage`.
    - On a customer page, the conversation timeline and summary show only with `inbox.read`. Otherwise it reads
      "Conversations are visible to the inbox team".
    - Linking a conversation to a customer needs both keys.
    - Spark's slot opens `/crm` for either key.
18. **Retention (O6) and erasure.** The daily sweep step `crm retention` handles:
    - **Messages:** logged messages are deleted 13 months after their `sentAt`. A conversation left with no messages
      is deleted.
    - **Customers:** a customer is a candidate when `lastActivityAt` is more than 24 months ago. The sweep then
      **recomputes** activity from the rows themselves: the customer's `updatedAt`, newest note, newest conversation
      `lastMessageAt`, newest deal `updatedAt` and newest linked quote `updatedAt`. Only a customer still inactive is
      deleted, through the same `eraseCustomer` path, audited `customer.retention-deleted` (ids only).
    - Customers with a `SHOPIFY` identity are skipped. They go with their source in Phase C.
    - **Deals with no customer** go 24 months after their `updatedAt`.
    - **Companies** with no customers and no deals go 24 months after their `updatedAt`.
    - **Quote rows stay** (for the books), with contact fields and the declined reason blanked when their customer is
      erased or deleted.
    - At most 5,000 customers and 50,000 messages per sweep. A backlog drains over the following days.
19. **Follow-up tasks use `Task.requestId`, not a new `Task.conversationId` column.**
    - Key: `followup:<conversationId>:<episode ms>`. The episode instant is stored on the conversation
      (`episodeAt`): the `sentAt` of the first customer message after ours (a second customer message doesn't change
      it), or `waitingSince` once waiting runs past 7 days.
    - The conversation records its open task (`followUpTaskId`, a plain string), so closing needs no prefix scan
      (a `LIKE 'prefix%'` can't use the btree under Neon's collation).
    - Creation runs under the conversation's row lock, and the existing `@@unique([brandId, requestId])` makes a retry
      a no-op.
    - No Task migration is needed, which avoids a merge clash with the tasks stream.
    - The task links to `/crm?tab=follow-ups&c=<id>`.
20. **The inbox role (O3)** is the PROJECT role on the brand that is not a client grant, holds `tasks.read` and
    `inbox.read`, and has the most active `BrandMember` holders (ties go to the oldest role).
    - The follow-up goes to the conversation owner when they still pass `canBeAssigned` for a CRM task, else to that
      role (Manager, Approver and Project admin are project roles, so B&C normally has one), else to **nobody**.
    - An unowned CRM task is seen by `tasks.all` holders who also hold a CRM key (Owner, Admin, Project admin).
    - In a workspace whose people are all on workspace roles (no project roles), follow-ups are therefore unowned
      until someone takes them. The queue itself shows every conversation either way.

## Data model (Phase A)

All new models are brand-owned. Each has the composite `brand Brand @relation(fields: [brandId, workspaceId],
references: [id, workspaceId], onDelete: Cascade)` and the back-relations. Each enum `ADD VALUE` gets its own
migration. Migrations use the `20261127130000`+ block.

```prisma
enum QuoteStatus { … DECLINED }                 // 20261127130000_quote_status_declined (ADD VALUE only)
model Quote { … declinedReason String?; dealId String? (SetNull); customerId / conversationId become FKs (SetNull)
              versions QuoteVersion[] }

model QuoteVersion { id; workspaceId; brandId; quoteId (Cascade); version Int; lines Json; discount Json?; note String?;
                     totals Json; sent Boolean; createdById String? (SetNull); createdAt
                     @@unique([quoteId, version]) }

model Company   { id; workspaceId; brandId; name (≤200); website String? (http/https); ownerId String? (SetNull);
                  createdAt; updatedAt; @@index([brandId, name]) }
enum CustomerSource { MANUAL QUOTE SHOPIFY INBOX }
model Customer  { id; workspaceId; brandId; companyId? (SetNull); displayName (≤200); role String? (≤100);
                  language String? (≤35); source; ownerId? (SetNull); nextAction? (≤200); nextActionDue? @db.Date;
                  lastActivityAt DateTime @default(now()); createdAt; updatedAt
                  @@index([brandId, lastActivityAt(sort: Desc)]) @@index([brandId, companyId]) @@index([lastActivityAt]) }
enum IdentityKind { EMAIL PHONE INSTAGRAM MESSENGER SHOPIFY }
model CustomerIdentity { id; workspaceId; brandId; customerId (Cascade); kind; value (≤254); createdAt
                  @@unique([brandId, kind, value]) @@index([customerId]) }
model CustomerNote { id; workspaceId; brandId; customerId (Cascade); authorId? (SetNull); text (≤4000); createdAt
                  @@index([customerId, createdAt]) }

enum ConversationChannel { LOGGED INSTAGRAM MESSENGER }
enum MessageMedium { EMAIL PHONE IN_PERSON WHATSAPP OTHER }
model Conversation { id; workspaceId; brandId; channel; connectionId String?; externalThreadId String?;
                  customerExternalId String?; customerId String? (SetNull); subject String? (≤200);
                  ownerId? (SetNull); nextAction?; nextActionDue? @db.Date;
                  lastMessageAt DateTime; lastFromCustomer Boolean; waitingSince DateTime?; closedAt DateTime?;
                  summary String?; summaryThrough DateTime?; createdAt; updatedAt
                  @@unique([connectionId, externalThreadId])                  // NULLs distinct: LOGGED rows unaffected
                  @@index([brandId, closedAt, lastMessageAt(sort: Desc)])     // the queue
                  @@index([brandId, nextActionDue]) @@index([customerId]) }
model ConversationMessage { id; workspaceId; brandId; conversationId (Cascade); externalId String?; medium MessageMedium?;
                  fromCustomer Boolean; text (≤4000); attachments String[] (types only); loggedById? (SetNull);
                  deletedAt DateTime?; sentAt; createdAt
                  @@unique([conversationId, externalId]) @@index([conversationId, sentAt]) @@index([sentAt]) }

enum DealStage { NEW CONTACTED PROPOSAL NEGOTIATION WON LOST }
model Deal      { id; workspaceId; brandId; stage @default(NEW); title (≤200); customerId? companyId? conversationId? (SetNull);
                  value Decimal?(14,2); currency String?; ownerId?; nextAction?; nextActionDue? @db.Date;
                  closedReason String?; closedNote String? (≤500); stageChangedAt; closedAt?; createdAt; updatedAt
                  @@index([brandId, stage, updatedAt]) @@index([customerId]) @@index([updatedAt]) }
```

Migrations, numbered in build order:
- `130000_quote_status_declined`: the enum value only.
- `130100_quote_declined_reason`.
- `130200_quote_version`.
- `130300_crm_records`: Company, Customer, identities, notes, their enums; the `Quote.customerId` FK after nulling
  stray values; the merge-suggestion expression index.
- `130400_conversations`, with the `Quote.conversationId` FK.
- `130500_deals`, with `Quote.dealId`.

**User ids (`ownerId`, `authorId`, `loggedById`, `createdById`) are plain `String?`, as on `Quote`**: no `User`
back-relations, and a removed member's id shows as "Former member". Every FK column has an index on the referencing
side (Review changes, Performance 2).

`lastActivityAt` is bumped by writes to the customer, its notes, messages on its conversations, its deals and its
linked quotes. It is a hint for the retention candidate query only. The deletion itself recomputes activity
(Decision 18).

## Global constraints

The Phase 3 plan's constraints apply.
- **Scoping:** every query is scoped by `workspaceId`/`brandId`. Another brand's id is a 404.
- **Shared code:** `shared/` is edited in the server repo, then `npm run sync:shared`, and the copies are committed in
  web and mobile.
- **SQL:** raw SQL is tagged only.
- **Customer data:** names, emails, phones, message, note and deal text and titles, and reasons never go into logs,
  job payloads, `Job.lastError`, audit metadata, error strings or AI-usage records. Audit metadata carries ids,
  counts, field names and lengths.
- **AI input:** customer text is delimited (`<customer_messages>`) with `<>` stripped. AI output is shown as plain
  text.
- **Web:** English copy, a 12 px floor, no new pollers, no `dangerouslySetInnerHTML`.
- **Commits:** what changed and why. No tests, co-author or URLs in the message.
- **Builds:** never `next build`.
