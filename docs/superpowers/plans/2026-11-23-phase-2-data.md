**Goal:** B&C sees Search Console clicks and positions, how each published post did, and Shopify orders and revenue, then Meta Ads spend and ROAS, can print any of it and export the ads table, all read from our own database and refreshed by daily jobs.

**Architecture:** One `DataSource` row per brand, source and external id (site, ad account). One job type `data.sync` on the existing Postgres queue fills daily rows (`SearchDay`, `PostMetric`, `ShopOrder`, `AdDay`); the daily sweep only enqueues; screens read only those tables through brand-scoped routes. Provider calls live in one client module per source; client tests inject a `fetch` stub with tiny inline fixtures, so every task is built and tested before any external approval arrives.

**Tech Stack:** Next.js route handlers, Prisma 6 on Postgres, zod, vitest (`npm test`, `npm run test:db`); web Next.js + React behind `WEB_FEATURES` flags; shared types synced with `npm run sync:shared`.

**Estimate:** 20.5 dev days = build on fixtures; approvals are calendar time not counted. Core 13.5 d (Tasks 1a–8: Search Console, post metrics, Shopify orders, print), then Meta Ads 7 d (Tasks 9–11, on fixtures, after the core ships). Held money settings (H1) add ~2 d when the owner answers, 22.5 d in all, inside the roadmap's 23.

## Why

B&C's feature list has Website/SEO, Social, CRM and Ads sections that today show nothing measured: the `GOOGLE` connection asks for `webmasters.readonly` but nothing reads it, Meta/Instagram/Threads ask for insight scopes but no metric is stored, Shopify syncs products only, and there is no ads connection. Without numbers in our DB, Phase 3 (digest, quotes, Google Ads) and every report has nothing to say.

## Decisions (owner)

Settled by the roadmap; listed so the implementer doesn't relitigate them.

1. Every source fills daily rows from background jobs on the existing queue. Screens read only our DB and show the last sync time. Outside data is never fetched during page load.
2. Search Console: Google permission is already granted at connect; add a site picker; daily rows; the last 3 days are re-read every run.
3. Post metrics for published Instagram, Facebook and Threads posts; posts under 30 days old are refreshed, older ones keep their final numbers.

7. A printable report (browser print to PDF) and an ads CSV/Excel export reusing `server/api/xlsx.ts` / `server/api/csv-export.ts`.
8. Each half-built module behind a web feature flag; no new fast pollers; dates in the brand's time zone; shared types via sync.

## My calls (owner may override)

1. **Permission keys:** `crm.read` ("See orders and sales totals", group `crm`) and `ads.read` ("See ad spend, results and budgets", group `ads`). Search Console and post metrics stay under `analytics.read`. Connecting Meta Ads and picking a site or ad account uses `integrations.manage`. Granted to Owner/Admin (code), Project admin (`PROJECT_KEYS`) and Manager; **not** to Creator, Approver, Viewer or Client reviewer (open question 1). **The server enforces these, not the UI** (see Route permissions).
2. **Meta Ads is a new provider `META_ADS`** with its own OAuth adapter, scope `ads_read` only, one connection per ad account (like Facebook Pages). It never shares a token with `META`/`INSTAGRAM`.
3. **Provider days are kept as the provider reports them.** Search Console days are Pacific time; Meta Ads days are the ad account's time zone; the screen labels them when they differ from the brand's zone. Shopify orders and post-metric snapshots are bucketed by us in the brand's zone (`BrandProfile.timeZone ?? DEFAULT_TIME_ZONE`).
4. **Orders are stored one row per order (no customer data)** and summed per brand-local day in SQL on read. No rollup table until a brand passes ~100k orders in a range (ceiling noted in code). An updated or refunded order is upserted and the day's total follows.
5. **Search Console v1 stores SITE and PAGE** per day (QUERY when someone asks); top 500 pages a day by impressions. Position is stored as `positionSum = position × impressions` so range averages are impression-weighted; CTR is computed on read. Page sums are below the site total (top-N cap); the screen says so.
6. **Post metrics are lifetime snapshots**: one row per published post per brand-local day it was read; after day 30 only the final row is kept. Instagram stories are skipped (open question 4).
7. **ROAS** on Ads is Meta-reported (purchase value ÷ spend), labelled. "Shopify revenue ÷ ad spend" waits for H1 (needs FX and the revenue definition).
8. **No polling for data screens.** They load once and on window focus. "Sync now" queues a job and says "Queued; numbers update in a few minutes".
9. **No app-wide mock.** Client tests inject a `fetch` stub with tiny inline fixtures (header `// recorded <date>, API vX`). If a dev walkthrough needs sample data later, add a flag then; it must throw at boot in production and mark DTOs "Sample data".
10. **Flags (three):** `data` (Search, Social tabs and print), `sales`, `ads` in `WEB_FEATURE_LIST`. The server needs no flag: jobs only run for a brand with a `DataSource` row, and rows are only created from flagged screens.
11. **On disconnect** rows are kept and syncing stops; rows are purged with the brand (cascade).

## Sync rules (all sources)

One job type `data.sync`, payload `{ dataSourceId, mode: "daily"|"manual"|"backfill", from?, to? }`, a switch on `DataSource.kind`. `maxAttempts` 3.

| | Search Console | Post metrics | Shopify orders | Meta Ads |
|---|---|---|---|---|
| daily key | `data:<sourceId>:<day>` | same | same | same |
| backfill key | `data:<sourceId>:backfill:<updatedAt epoch>:<windowStart>` | — | `data:<sourceId>:backfill:<updatedAt epoch>` | as Search Console |
| daily window | today−3..today−1 (PT) | due posts (decay below) | `updated_at ≥ cursor − 1 h` | today−7..today−1 (account tz; attribution settles over 7 days) |
| backfill | 90 days, 30-day windows | none | 60 days (`read_orders` limit) | 90 days, 7-day windows (`limit=500`; halve on "reduce the amount of data") |
| write | buffer window; per day one transaction: delete `(brandId, siteUrl, dimension, day)` + insert | upsert `(attemptId, day)` | one `INSERT … ON CONFLICT DO UPDATE` per page (`unnest`) | buffer window; one transaction: delete `WHERE brandId, platform, accountId AND day BETWEEN` + insert |
| rate limit | ≤ 5 req/s per site; stop on 429 | Graph batch ≤ 50 per call, grouped by connection; stop on code 4/17/32/613 | `shopifyQuery` throttle wait | `x-business-use-case-usage`; stop above 75 % |

- **One job at a time per source, no lock.** Idempotency keys plus delete-then-insert per day make a repeated job write the same rows. Backfill is the same job on a resumable window: one window at a time, the next chained when one finishes (no parallel chunks). A daily job that finds a running backfill for the same source re-queues itself at `runAt + 5 min` instead of completing.
- **`syncedThrough`:** null = daily covers only today−3..today−1. Backfill walks windows oldest first and advances `syncedThrough` only contiguously; set to the backfill end when done. Backfill keys carry `DataSource.updatedAt` so a re-pick re-runs; the daily key doesn't.
- **Partial pages:** a day is written only when every query/page for it succeeded; a mid-pagination stop writes nothing and keeps `syncedThrough`. A stopped run records `reason = "partial"` ("Some days are still loading"), not an error. Shopify is the exception: upserts are safe per page, so its cursor advances per saved page.
- **Manual "Sync now":** check-then-create like `requestCatalogSync`, plus a per-brand+user limit of 3/h per source, skipped if the source synced under 5 min ago.
- **Job handler:** re-reads `DataSource` by id with brand, workspace and kind; loads the connection via `dataSource.connectionId` and asserts the same brand; a switched-off or deleted source is a no-op.
- **Token expiry:** `ReconnectNeeded` → `status = ERROR`, `reason = "reconnect"`, not retried (runner's `refused` rule extended to `data.sync`). A missing insight/ads permission (Graph code 10 or 200–299) → `reason = "permission"`, the connection stays ACTIVE (publishing keeps working). Only OAuth error 190 marks the connection through `markReconnect`; an expired 60-day Meta Ads token landing there is expected.
- **Provider rate limit:** 429 or a Graph throttle code stops the run as partial (not thrown), so backoff isn't burned on an hourly quota.
- **Queue fairness:** `claimNextJob` skips `data.%` jobs when 2 are already RUNNING, so data never starves publishing. The sweep spreads `runAt` by hash(sourceId) mod 120 min.

## Review focus

1. Daily + Sync now + backfill for one source: one runs at a time, rows identical to a single run; daily waits behind a running backfill.
2. A re-read where Google drops a page or Meta drops a campaign for a day: the old row is gone, totals match the provider.
3. A missing insights or ads permission never marks the publishing connection "Needs reconnect"; a revoked token does and stops retries.
4. An order at 23:30 UTC for a Europe/Paris brand lands on the next local day; a refund on an old order changes that old day.
5. A brand with EUR shop and INR ad account: no number ever adds the two.
6. Client reviewer or Viewer: no sales or ads numbers in any route, print view or export.
7. Data jobs never delay publishing jobs.
